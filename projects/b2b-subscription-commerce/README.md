# B2B 구독 커머스 기업 CRM 구축

> 고객사 보안상 소스 코드와 고객사명은 공개하지 않습니다. 업무 구조와 설계 판단만 정리합니다.

| 항목 | 내용 |
|:--|:--|
| 구분 | 고객 구축 프로젝트 (Salesforce 파트너사 뉴브릭) |
| 기간 | 2026.04 ~ 진행 중 |
| 역할 | 설계부터 Apex·Flow·배포까지 단독 수행 |
| 제품 | Sales Cloud, Service Cloud, Agentforce, Data Cloud |
| 상태 | Sandbox 구축 완료 항목 있음, 1차 Go-Live 2026-10 예정 |

## 업무 문제

- 사업 유닛마다 영업 방식이 달라 파이프라인이 여러 갈래로 나뉘어 있었습니다.
- 견적은 Excel로 수기 작성했습니다.
- 고객 상담이 전화·채팅·메일로 흩어져 있고, 상담 기록을 여러 곳에 이중으로 남겼습니다.
- 청구가 고객사 단위로 묶여 있어 서비스별 매출을 나눠 보기 어려웠습니다.
- 매출 데이터의 원천은 고객사가 자체 운영하는 ERP였습니다.

## 구축 범위

- 유닛마다 영업 단계가 달라 Opportunity를 유닛별 Sales Process로 나눴습니다.
- 계약과 계약 라인을 중심에 두고 서비스·유형자산을 Asset으로 구분했습니다.
- 고객별 잔액과 청구·매출 데이터를 CRM에서 롤업으로 볼 수 있게 했습니다.
- Service Cloud로 상담 채널을 모았습니다.
- 웹챗 앞단에 AI Service Agent를 두고 Knowledge로 1차 응대하게 했습니다. 필요하면 상담원에게 이관합니다.

## 설계 판단

**CRM을 정본이 아니라 작업 레이어로 두었습니다.**
현업은 ERP에서 데이터를 만드는 데 익숙했습니다. CRM이 매출 정본 역할을 흉내 내면 두 시스템이 어긋납니다. 그래서 매출은 ERP에서 흘러오게 하고, CRM은 영업·상담이 일하는 자리로 잡았습니다.
기각한 대안: CRM을 중심에 두고 데이터를 모으는 통합. CRM만으로 끝나는 분석은 포기하고 ERP 연동 품질에 기대는 쪽을 택했습니다.

**오입력 방지 장치를 만들지 않았습니다.**
견적 라인에서 프로모션을 잘못 고를 수 있다는 우려가 있었습니다. 막으려면 필드와 Flow를 추가하거나 입력 항목을 늘려야 했습니다. 실수 하나를 막자고 관리 대상과 입력 부담을 늘리지 않기로 했습니다. 잘못된 선택이 실제로 쌓이면 그때 가장 가벼운 Validation Rule을 넣습니다. 방지 대신 모니터링 조건을 둔 셈입니다.
기각한 대안: 필드와 Flow로 선택지를 좁히는 방지 장치. Lookup Filter만으로는 부모 레코드의 값을 조건으로 읽지 못해 장치가 커질 수밖에 없었습니다.

**값을 필드로 복사하지 않고 수식으로 읽었습니다.**
평가 입력 화면에서 상위 레코드의 서비스 정보가 저장 전에 보여야 했습니다. 필드를 새로 만들어 복사하는 대신 부모 관계를 따라 올라가는 수식으로 대체했습니다. 쓰지 않게 된 Lookup도 제거했습니다. 복사본이 없으니 값이 어긋날 일도 없습니다.
기각한 대안: 값을 채우는 장치를 여러 화면에서 쓰는 범용형으로 만드는 안과, 다른 기능에 있던 방식을 전용으로 복제하는 안. 값이 이미 정해지는 자리를 찾자 둘 다 만들 필요가 없었습니다.

## 재사용 원칙

다른 고객 프로젝트에도 그대로 가져가는 판단 기준입니다.

- **정본 판정을 먼저 합니다.** 기능이 아니라 현업이 어디서 데이터를 만드는 데 익숙한지, 이력이 어디에 남는지로 시스템을 가릅니다.
- 문제가 실증되기 전에는 최소 장치로 버팁니다. 필드·자동화 하나마다 유지보수와 입력 부담이 붙으므로, 방지 장치 대신 모니터링 조건을 둡니다.
- 입력 방식과 화면은 현업에 맞춥니다. 데이터 모델과 정본 구도는 양보하지 않습니다.

## 이 문서에 없는 것

- 고객사명과 사업 유닛명을 뺐습니다.
- 성과 수치(건수·금액·비율)를 뺐습니다.
- 소스 코드, 필드 API명, 내부 도구와 외부 서비스의 제품명을 뺐습니다.
- 실제 화면 캡처 대신 일반 레이블로 다시 그린 도식만 넣었습니다.
